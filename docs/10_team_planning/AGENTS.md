## 1. 事实源

- `01_development_team_proposal.md`：组织能力基线。
- `02_kinbot_team_recruitment_requirements.csv`：岗位编号、名称和筛选口径基线。

- `92_senior_agent_architect_jd.md`：岗位 `22` 高级 Agent 架构师基线。
- `93_motion_control_algorithm_engineer_jd.md`：岗位 `15` 高级运动控制算法工程师基线。

候选人具体状态、个人判断和面试题以 `91` 为准，不再复制到 `AGENTS.md`。

## 2. 新增资料处理

- `input/01_candidate_resume/` 根层只放待处理资料。
- 新增简历、初试反馈、面试总结或录音转写后，先更新 `91` 的输入清单、流程口径、总表、个人小节和建议动作。
- 已吸收资料移动到 `input/01_candidate_resume/archive/YYYY-MM-DD_processed/`；同日多批可用 `YYYY-MM-DD_<topic>_processed/`。
- 原始 PDF、扫描件和转写输入默认本地留存，不进入正式版本；正式判断只写入台账。
- 简历筛选与面试后判断必须分开，不能把关键词或自述当成已验证能力。

## 3. 岗位与候选人判断原则

- 新增岗位或调整岗位编号 / 名称时，先更新岗位 CSV，再同步输入命名、`91` 和目录索引。
- 必须验证真实 owner 边界、生产规模、异常恢复、安全约束、评测闭环和团队责任，不能因出现 `RAG / Agent / LangGraph / MCP / VLA / URDF` 等关键词直接升级岗位判断。
- 相邻岗位适配要拆清“主定位”和“可观察方向”，不得为了推进候选人而模糊岗位责任。
- 技术深面后进入总经理终面时，区分“有条件推进”与“无保留强推”；终面重点转向动机、亲自落地、协同方式、薪资 / base、岗位定位与 offer 条件。
- offer 接受、放弃、流程结束或入职前变化必须同步刷新顶部状态、总表、个人小节和建议动作；历史评价只作留痕。

## 4. 重点岗位边界

- 岗位 `01`：应用后端 / 平台架构与 AI 融合。重点验证服务边界、设备云、可观测、高可用、灰度、AI 工程化和完整架构 owner 证据。
- 岗位 `09`：本体系统工程。重点验证系统约束、跨域取舍、阶段门、整机责任与组织授权；特殊关键岗按线下真机交流和保密边界执行。
- 岗位 `10`：结构与传动。涉及双臂前瞻、URDF / 仿真时，验证可信数字本体、参数可信和 sim-to-real，不改变第一代轮式无臂主线。
- 岗位 `11`：Agent 应用开发。重点验证物理设备工具调用、权限、参数校验、幂等、回滚、审计、Plan-Execute-Verify 和 AgentOps，不等同于总体架构 owner。
- 岗位 `15`：SoC 侧运动控制算法。重点验证状态估计、经典控制产品化、渐进强化学习、SIL / HIL / 真机闭环，以及与 MCU 硬实时执行层的边界。
- 岗位 `16`：系统集成测试负责人。只有具备本体、端侧、云侧、App、服务链路、SIL / HIL / E2E、故障注入和试点质量闭环证据时才按负责人主推。
- 岗位 `22`：具身智能 Agentic System 总体架构 owner。重点验证 Agent Runtime、Tool / Action 安全、AgentOps / 评测和技术牵引，与岗位 `01 / 11` 明确分工。

## 5. 面试工作流

- 先问候选人的原生判断，再介绍项目，最后回到岗位责任，避免把候选人复述项目口径当成理解。
- 项目介绍保持统一事实：第一代轮式无臂主线与双臂前瞻线并行，前瞻线不得拖累一代量产。
- 需要新增 CTO 题包时，默认准备 `10` 道候选题，现场选 `6～8` 道；显式代入 Kinbot 的题默认最多 `1` 道。
- 线上综合面可控制在 `50` 分钟内，以口头分层、关键链路追问和现场选题替代强制画图，但不能降低 owner 证据要求。

## 6. 完成检查

- 当前流程状态、总表、个人小节和末尾建议是否一致。
- 岗位编号、名称、JD、输入命名和筛选口径是否一致。
- 待处理输入是否已经吸收并归档。
- 未确认的公司、岗位或去向是否明确标为用户口径 / 待确认。
- 是否保护候选人隐私，避免将本地输入资料误纳入版本管理。

拆分前的个人专项检查词和历史只读核查命令保留在 `docs/00_governance/agent_rules/AGENTS_v1.64_full_archive.md`，只在追溯旧规则时读取。
