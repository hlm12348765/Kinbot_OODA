## 1. 文档目的

本文档用于把 `V1` 机载药箱从“储物仓能力要求”推进到可下发工程评审的决策稿。

它不替代 [13_medication_storage_and_indoor_delivery_requirements.md](../02_p1_architecture/13_medication_storage_and_indoor_delivery_requirements.md)。`13` 号文档继续作为储药与室内递送的需求和边界事实源；本文聚焦 `P2` 层的系统取舍：

1. 无机械臂前提下，一代最小可交付用药闭环是什么；
2. 仓门采用什么开合方式；
3. 取药、放回、服药确认分别靠什么检测；
4. 视觉判断与低层传感器如何分工；
5. 异常、卡滞、防夹和故障保护如何处理；
6. 哪些主线文档需要后续回写。

## 3. 决策摘要

当前推荐结论：

| 项 | 决策 |
| --- | --- |
| 总体方案 | `P`：`V1` 采用一体化机载药箱 / 储物仓，定位为躯干内置的轻量电动浅抽屉 / 托盘。 |
| 最小闭环 | `提醒 -> 审批 -> 到人 -> 驻停 -> 开仓 -> 用户自取 / 放回 -> 确认 -> 关仓 -> 记录 -> 家属通知或升级`。 |
| 无手臂边界 | 机器人不抓取、不分拣、不递到手；机器人只把已装载物品移动到可交互位置，并完成开仓、提示、检测和审计。 |
| 开合方式 | 默认采用前向电动浅抽屉 / 托盘式开合；顶部翻盖、侧向大抽屉、多格 vending 机构仅作为后续备选或边界验证。 |
| 取药检测 | 以仓内物品存在状态传感为主，视觉和语音确认为辅；不能只靠视觉判定取药成功。 |
| 放回检测 | 以物品存在状态重新稳定为主，结合用户确认；放回不等于服药失败，需独立记录。 |
| 服药确认 | `已取出` 与 `已服用` 分开记录；`V1` 不把“药品消失”自动写成“已服用”。 |
| 防夹策略 | 防夹为硬门槛，必须由低层实时传感和电机控制闭环兜底，视觉只做前置观察和复核，不作为唯一安全保护。 |
| Phase 5 | 把机载药箱纳入 `V2 健康闭环`、`V4 安全与降级`、`M2/M4/M5` 证据包候选字段；不新增独立在线平台。 |

一句话版本：

> `V1` 机载药箱不是“机器人自动拿药”，而是“机器人把受控药品或小物件安全送到人旁边，打开可取空间，引导用户自取 / 放回，并把取出、服用确认、异常和通知做成可审计闭环”。

## 5. 无手臂最小可交付闭环

### 5.1 闭环定义

`V1` 最小可交付闭环按 `9` 步组织：

```mermaid
sequenceDiagram
    participant Plan as 计划/事件
    participant Gate as 安全审批
    participant Nav as 到人导航
    participant Box as 机载药箱
    participant User as 老人/保姆
    participant Record as 记录/通知

    Plan->>Gate: 提交用药/递送动作提议
    Gate-->>Plan: 批准/拒绝/降级/待确认
    Plan->>Nav: 到达可交互位置
    Nav->>Box: 驻停、制动、朝向确认
    Box->>User: 语音/屏幕提示并开仓
    User-->>Box: 自取、放回、拒绝或无响应
    Box->>Gate: 取放状态和异常复核
    Gate->>Record: 输出结果状态
    Record->>User: 关闭任务、通知家属或升级
```

### 5.2 最小完成标准

一次用药递送任务只有同时满足以下条件，才能记为“本体递送闭环完成”：

1. 任务通过 `safety_compliance_authorization` 审批；
2. 机器人到达可交互位置，并在开仓期间保持驻停和制动；
3. 仓门打开到可取状态，且开仓过程无防夹 / 卡滞异常；
4. 系统获得 `已取出 / 已放回 / 拒绝 / 无响应 / 中断 / 未确认` 中至少一种结构化结果；
5. 仓门最终关闭或进入受控异常状态；
6. 记录写入 `Task / CareEvent / WorldEvent`，必要时通知家属或进入升级链。

说明：

- “已取出”不是“已服用”。
- “已服用”需要语音、屏幕点击、App 远程确认、保姆协助确认或后续更强证据支持。
- 如果用户拿走药但未确认服用，记录应为 `已取出，服药未确认`，而不是自动成功。

## 6. 开合方式决策

### 6.1 推荐方式

推荐采用：

> 躯干正面一体化电动浅抽屉 / 托盘，低速推出，固定行程，带物品止挡和柔和导向，开仓后用户自取或放回。

关键约束：

1. 开口朝向机器人正前方，便于机器人到人后直接面向用户交互；
2. 仓体高度应服务坐姿和站姿老人，不追求最大容量；
3. 抽屉推出后形成稳定浅托盘，避免药盒滚落；
4. 仓门开合不得遮挡主要交互屏、主摄关键视线和近场安全观察；
5. 仓门打开后机器人不得继续移动；
6. 关仓必须低速、限力、可中断、可反向释放。

### 6.2 备选方式比较

| 开合方式 | 结论 | 主要问题 |
| --- | --- | --- |
| 前向浅抽屉 / 托盘 | 推荐 | 需要处理前向空间占用和防夹，但最符合到人交互和用户自取。 |
| 侧向抽屉 | 观察 | 需要机器人额外调整朝向，用户左右手、轮椅和床边姿态差异会增加交互复杂度。 |
| 顶部翻盖 | 不推荐为默认 | 对坐姿老人不友好，容易与屏幕 / 躯干上表面交互冲突，落尘和可视性也更差。 |
| 多格旋转药仓 | 后续观察 | 防错拿价值更高，但机械复杂度、噪声、寿命、产测和售后压力大。 |
| 机械臂或末端执行器 | 阻断当前主线 | 超出“不要求物理操作”和无手臂边界，直接改变产品定义和成本结构。 |

## 7. 取药 / 放回检测

### 7.1 状态拆分

`V1` 不应把用药结果压成一个布尔值。建议至少拆成以下状态：

| 状态 | 含义 | 是否等于服药成功 |
| --- | --- | --- |
| `loaded` | 已装载目标物或本次任务物品 | 否 |
| `presented` | 已到人并开仓提示 | 否 |
| `retrieved` | 物品已从仓内取出 | 否 |
| `returned` | 物品已被放回仓内 | 否 |
| `taken_confirmed` | 用户或授权照护者确认已服用 | 是，但需保留确认来源 |
| `refused` | 用户拒绝取药或服药 | 否 |
| `unconfirmed` | 取放状态或服药状态无法确认 | 否 |
| `interrupted` | 因故障、安全、低电、定位或用户无响应中断 | 否 |

### 7.2 取出检测

取出检测采用“三层证据”：

| 层级 | 证据 | 主责 |
| --- | --- | --- |
| 低层物理证据 | 仓门已开、物品存在状态从有到无、重量 / 接触 / 位置状态变化稳定 | `S1` 机构与传感 |
| 外部视觉证据 | 已授权人靠近、手部进入可取区域、目标物疑似离开托盘、无人夹在关仓区域 | `S2/S4` 视觉与状态 |
| 交互确认证据 | 用户语音确认、屏幕确认、保姆确认或家属远程确认 | `S3/S6` 交互与伴生系统 |

最低要求：

1. `retrieved` 必须至少有低层物理证据；
2. 如果低层物理证据和视觉证据冲突，应写为 `unconfirmed`，并触发用户确认；
3. 如果身份不确定，不能把取出结果写成敏感用药成功，只能写成“物品状态变化待确认”。

### 7.3 放回检测

放回检测同样以物理证据为主：

1. 仓门处于打开或受控半开状态；
2. 物品存在状态从无到有，并在短时间内稳定；
3. 重量 / 接触 / 位置状态落在本次任务允许区间；
4. 用户确认“放回”或系统通过交互追问确认。

放回的记录语义：

- 用户放回药品，记录为 `returned`；
- 如果已取出后放回且未确认服用，记录为 `retrieved_then_returned`；
- 如果放回物与本次任务预期不一致，记录为 `returned_unmatched`，不得自动关闭任务；
- 如果低层证据显示放回，但视觉看到物品掉落或用户仍持有疑似目标物，应进入 `unconfirmed`。

### 7.4 装载检测

`V1` 不追求复杂仓内自动盘点，但必须支持单任务级装载记录：

1. 老人、子女或保姆通过 App、语音或屏幕登记本次装载；
2. 系统记录 `object_id / task_id / target_person_id / loaded_at / loaded_by / expected_window`；
3. 仓内物品存在状态与登记状态不一致时，不允许自动进入递送；
4. 药品名称、剂量、禁忌和处方来源仍由健康链、App 或人工录入治理，不由仓内传感器自行推断。

## 8. 视觉判断与传感器分工

### 8.1 分工原则

视觉负责“理解场景”，低层传感器负责“保证动作安全和状态可信”。

不允许：

1. 用视觉替代防夹硬保护；
2. 用云侧视觉判断开仓是否安全；
3. 用单次视觉识别把“药已取走”直接写成“药已服用”；
4. 为药箱重新引入默认 `ToF` 或主动传感器堆叠，绕开当前纯视觉和低复杂度主线。

### 8.2 低层传感器最小集合

建议 `V1` 机载药箱采用以下最小传感集合：

| 传感 / 信号 | 作用 | 硬性等级 |
| --- | --- | --- |
| 仓门位置 / 到位信号 | 判断开、关、半开、不到位 | 必须有 |
| 电机电流 / 扭矩异常 | 识别卡滞、阻塞、异常负载 | 必须有 |
| 防夹触边 / 接触保护或等效低层保护 | 对夹手风险做实时中断 | 必须有 |
| 锁止 / 释放状态 | 防止运动中开仓或开仓中移动 | 必须有 |
| 物品存在 / 重量 / 接触状态 | 判断取出、放回、空仓和异常 | 应该有 |
| 温湿度或药品环境监测 | 特殊药品才需要 | 可以有 |
| 多格位 ID / 细粒度盘点 | 多药品管理增强 | 可以有 |

说明：

- 上表中的防夹、位置、电流、锁止属于机构安全与执行传感，不改变一代“外部感知主线纯视觉”的边界。
- 若物品存在传感无法进入首批结构，取出 / 放回应降级为“视觉 + 语音 / 屏幕确认”，但该方案只能为 `W`，不能作为强闭环成功判据。

### 8.3 视觉判断职责

视觉只承担以下职责：

1. 确认机器人面前是否是目标用户或授权照护者；
2. 观察开仓区域是否有明显身体部位、衣物或其他障碍物；
3. 判断用户是否有伸手取物、放回、拒绝或无响应行为；
4. 识别物品是否疑似掉落在仓门前或地面；
5. 为事后复盘保留端侧结构化事件，不默认回流原始视觉数据。

视觉不承担：

1. 最终防夹；
2. 药品处方正确性判断；
3. 服药进入人体的医学确认；
4. 云侧远程开仓安全判断。

## 9. 异常与防夹策略

### 9.1 基础安全规则

仓门动作必须遵守以下硬规则：

1. 机器人运动中禁止开仓；
2. 仓门打开时禁止底盘移动；
3. 开仓前必须完成驻停、制动、目标用户 / 照护者确认和前方交互区检查；
4. 关仓前必须提示用户，并等待短暂安全窗口；
5. 关仓过程必须低速、限力、可立即停止或反向释放；
6. 任一防夹、卡滞、位置异常或电流异常触发时，立即停止仓门动作；
7. 防夹保护失效、仓门卡滞且存在夹伤风险时，映射为 `F7` 储物仓与执行机构安全故障。

### 9.2 异常处理表

| 异常 | 判定信号 | 处理 |
| --- | --- | --- |
| 防夹触发 | 接触保护 / 电流突升 / 位置不动 | 立即停止或反向释放，语音提示，记录 `compartment_pinch_prevented`，禁止继续自动关仓。 |
| 仓门卡滞 | 电机动作与位置变化不一致 | 停止仓门动作和底盘运动，提示用户远离仓门，进入受控恢复或故障保护。 |
| 关仓不到位 | 到位信号失败或锁止失败 | 不允许移动；提示用户检查；必要时请求家属 / 保姆确认。 |
| 物品状态冲突 | 重量 / 接触 / 视觉 / 用户确认不一致 | 标记 `unconfirmed`，不写成服药成功，触发交互确认。 |
| 身份不确定 | 视觉 / 声纹 / 交互身份不足 | 不开仓或降级为低风险提醒；敏感药品必须等待确认。 |
| 用户无响应 | 到人后无语音、手势或取物动作 | 关闭或保持受控开仓，按风险等级重试、通知家属或中断。 |
| 用户拒绝 | 用户明确说不吃 / 不取 | 记录 `refused`，关闭任务或按策略提醒家属。 |
| 低电量 | 剩余电量不足以支撑任务与回充 | 非紧急递送挂起；高风险用药可先完成当前确认，再回充。 |
| 定位异常 | 无法安全到人或重定位失败 | 不执行递送；转为语音 / App / 家属确认。 |
| 网络断开 | 云和 App 不可用 | 保留本地提醒、审批、开仓安全和暂存记录；暂停外部履约。 |

### 9.3 失败结果语义

失败不应统一写成“递送失败”。建议最小失败结果为：

| 结果 | 语义 |
| --- | --- |
| `blocked_by_safety` | 安全链阻断，如防夹、卡滞、障碍、身份不确定 |
| `blocked_by_authorization` | 授权或角色不满足 |
| `user_refused` | 用户拒绝 |
| `user_no_response` | 用户无响应 |
| `object_missing` | 应有物品不存在 |
| `object_state_uncertain` | 取放状态不可信 |
| `system_fault_f7` | 储物仓与执行机构安全故障 |
| `task_deferred` | 因低电量、定位、网络或时间窗暂缓 |

## 10. Phase 5 验证约束

### 10.1 对应验证域

机载药箱至少映射到以下验证域：

| Phase 5 域 | 药箱验证重点 |
| --- | --- |
| `V2 健康闭环验证` | 用药提醒、到人、开仓、取出、服药确认、家属通知是否形成可重复闭环。 |
| `V4 安全与降级验证` | 防夹、卡滞、低电、定位异常、传感冲突、身份不确定时是否保守处理。 |
| `V5 伴生系统与服务验证` | App 计划、远程确认、家属通知和后续服务适配是否接得上。 |
| `V6 试点执行与数据回收` | 取药 / 放回 / 拒绝 / 未确认等结果是否结构化回收。 |
| `M2 整机平台与 BOM 冻结` | 药箱机构是否进入受控重量、空间、功耗、可靠性和成本区间。 |
| `M4 安全 质量 合规闭环` | 防夹与药品敏感动作是否有验证和审计。 |
| `M5 供应链 制造 测试导入` | 仓门寿命、卡滞、装配、产测、售后和维修策略是否可执行。 |

### 10.2 最小证据字段

建议后续 Phase 5 模板吸收以下候选字段：

| 字段 | 含义 |
| --- | --- |
| `medication_task_id` | 用药 / 递送任务 ID |
| `approval_decision_id` | 审批结果引用 |
| `target_person_identity_state` | 目标用户身份确认状态 |
| `compartment_state` | `closed / opening / open / closing / blocked / fault` |
| `compartment_lock_state` | 锁止与运动互锁状态 |
| `anti_pinch_guard_state` | 防夹保护是否可用 |
| `anti_pinch_event_count` | 本次任务防夹触发次数 |
| `item_presence_state_before` | 开仓前物品存在状态 |
| `item_presence_state_after` | 关仓后物品存在状态 |
| `handoff_result` | `retrieved / returned / refused / unconfirmed / interrupted` |
| `medication_taken_confirmation` | `confirmed / denied / no_response / not_applicable` |
| `visual_handoff_observation` | 端侧结构化视觉观察摘要 |
| `sensor_disagreement_reason` | 视觉、物理传感、用户确认不一致原因 |
| `fallback_action` | 重试、通知家属、中断、转后续适配位等 |
| `fault_class` | 是否触发 `F7` 或其他关键故障 |
| `audit_event_id` | 审计事件引用 |

说明：

- 这些字段是本决策稿提出的候选最小字段，不等于已经完成实机验证。
- 不建议为药箱单独新增完整观测平台；应并入 `S7` 既有审计、回放和 Phase 5 证据结构。

### 10.3 阻断项

以下结果应阻断药箱进入量产预备主线：

1. 防夹保护不能稳定触发或触发后不能停止 / 释放；
2. 仓门打开状态下机器人仍可能移动；
3. 仓门关不严、锁止失败或卡滞后无可靠提示与故障记录；
4. 取出 / 放回 / 未确认无法结构化区分；
5. 系统把“取出”自动写成“已服用”；
6. App、云或坐席能绕过端侧审批直接开仓；
7. 机构显著损伤外观比例、重心、通行能力、噪声或可维护性。

## 12. 复杂度自检

现在的架构是不是太复杂了？

当前推荐方案的复杂度可控，原因是：

1. 不新增机械臂、不新增自动分药系统、不新增药箱专用主动传感主线；
2. 只把药箱作为 `T8` 对象落入既有 `S1/S3/S4/S5/S7` 工作包；
3. 传感器分工压缩为位置、锁止、电流 / 防夹、物品存在和端侧外部视觉观察；
4. 结果状态只区分取出、放回、服药确认、拒绝、未确认和中断，不追求医学级自动服药证明；
5. Phase 5 只新增候选证据字段，不新增独立平台。

如果后续把多格位自动盘点、复杂防错拿、机械臂递药、云侧视觉裁决或专用主动传感器重新加入默认主线，复杂度会明显失控，应先回到 `T8` 权衡表重新评审。

## 13. 当前结论

`V1` 机载药箱建议按 `P` 进入工程化细化，但带三个前置条件：

1. 防夹、卡滞、锁止和开仓不移动必须先过硬门槛；
2. 取药、放回、服药确认必须分开记录；
3. 机构容量和复杂度必须服从整机外观、重心、功耗、噪声、可靠性和 `5000 到 6000` 元 `BOM` 基线。

该方案能保住健康管理主价值和紧急用药 Demo 的产品化路径，同时不把 `V1` 推向机械臂、自动药柜或云侧医疗处置系统。
