本文件适用于 `docs/` 下全部文档；更深目录存在 `AGENTS.md` 时，同时遵守更具体的目录规则。

## 1. 文档格式

正式文档默认使用中文，头部至少包含：

- 文档标题
- 当前状态或用途
- 责任角色
- 版本历史入口

高频演进或超过 `500` 行的主线文档，不在正文累积详细版本流水；历史记录放入同目录的独立 `*_history.md`，正文只保留链接。短文档可以继续保留简版变更记录。

作者按责任角色命名：架构主线程使用 `Codex-架构师`，其他专项使用 `Codex-角色名`。

用词应优先采用约定俗成的日常表达或已有明确含义的专业术语。不得为了显得抽象而创造难懂的新词；确需引入新术语时，必须先定义。

## 2. 索引与变更记录

- 新增、重命名或移动正式文档时，先更新所在目录的 `README.md`。
- 影响仓库总入口或阶段入口时，再更新根 `README.md`。
- 目录级变化统一记录在根 `CHANGELOG.md`，不在多个子目录重复维护同一份目录变更日志。
- `AGENTS.md` 属于代理工作规则，不列入产品文档索引；新增规则包或规则目录时，只需在治理目录中保留入口。
- 根 `README.md` 只维护当前有效入口、阶段门入口和历史资料指针，不平铺全部历史材料。

## 3. 事实、提案与历史记录

- 已确认结论使用 `confirmed` 或自然中文明确说明“已确认”。
- 未经评审的内容必须标为“提案”“假设”“候选”或 `provisional`。
- 活跃 `provisional` 必须绑定明确承接项，写清内容、位置、冻结条件、目标阶段门和 owner。
- 详细候选内容只在受控载体中展开；其他主线文档只保留摘要与指针。
- 研究结论、申报叙事、候选方案和历史评审材料不得直接升级为主线事实。
- 真实仓库状态与文档冲突时，先核对事实，再修正文档。

## 4. 图示

结构分解、架构关系、流程、分层、状态或阶段门关系在图示能显著提升理解时应配图。

图示的正式展示格式为可缩放 SVG。Mermaid 只用于快速建模或生成 SVG；语义等价的 SVG 完成后，从正式正文删除 Mermaid，避免双图重复。新建或实质修改图时：

- 若先使用 Mermaid，必须据此生成语义等价的 SysML v2 风格 SVG；需要汇报时再提供 PNG。
- 按语义选择并标明 `GeneralView`、`InterconnectionView`、`ActionFlowView`、`StateTransitionView`、`SequenceView`、`GridView` 等视图类型，不得只模仿外观。
- Mermaid 源与 SVG 中的实体、过程、操作数、方向、分支条件和边界必须一致。
- SysML 图可为可读性合并重复 usage，但不得改变架构语义。
- 新增视图类型或正式模型语义时，维护可解析的 `.sysml` `view def` 并完成语法校验。
- 图与模型源不一致时，先核对模型语义，再同步修正 SVG。

## 5. 文档编辑顺序

- 先判断新输入影响哪些主线文档。
- 先更新系统级文档，再更新下游方案或专项文档。
- 最后检查目录索引、根 `CHANGELOG.md`、决策记录与项目管理状态是否需要同步。
- 不得无说明覆盖其他线程的明确修改；吸收专项结论时标明来源。
- 活跃主线文档目标控制在约 `500` 行；超过 `600` 行时说明继续保留单文件的理由，或拆出稳定附录。
